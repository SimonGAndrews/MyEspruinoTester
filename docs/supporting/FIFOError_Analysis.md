# Possible causes of the FIFO_FULL error
When the Gordon runner wraps each test it prepends bookkeeping state, a 250 ms keep-alive interval that prints JSON, and serializes the entire fixtures object into global.ESPRUINO_WIFI_FIXTURES = …; before the test body runs.

Compared with pasting test_connect_get_ip.js by hand, this makes the upload significantly larger and bursts additional traffic (keep-alive prints plus any fixture JSON) at the interpreter while it is still processing the incoming program. Because sendViaCLI simply invokes espruino <tempfile>—letting the CLI stream the whole wrapped file in one go—boards without hardware flow control can overrun the input FIFO during this burst.

The harness’ keep-alive loop continues to emit JSON until result is set. If the Wi-Fi test is still negotiating DHCP (which polls wifi.getIP() repeatedly via setTimeout), those extra print calls keep the interpreter busy, so hardware interrupts that enqueue characters (for example UART noise, Wi-Fi module debug output, or state-transition notifications the Espruino firmware pushes internally) have more time to pile up. On slow MCUs the interpreter may not drain the receive FIFO quickly enough, triggering FIFO_FULL even though the same test body succeeds when run without the additional keep-alive chatter in the REPL.

Fixture payload size can also matter: the runner embeds whatever JSON you pass via --fixtures inline in the uploaded script. Large credentials blocks (certificates, long passwords, etc.) become a single long line the CLI transmits as fast as it can. In a manual REPL session you typically paste the test first and populate fixtures interactively (or they already live in RAM), so the interpreter never has to ingest that large JSON blob under load. Streaming it during the automated upload gives the small Espruino receive FIFO more opportunities to overflow.

In short, the automated path stresses the interpreter with more inbound bytes (wrapper + fixtures) and extra background work (keep-alive printing) while the Wi-Fi stack is active, so boards that cope fine with the bare test in the REPL can report FIFO_FULL when driven by the scripted runner.
